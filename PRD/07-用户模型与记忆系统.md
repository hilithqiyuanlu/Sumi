## 1. 设计哲学

### 核心原则

- **记忆 = 用户模型**：一套数据结构同时服务 prompt 注入和行为决策。USER_MODEL.md 替代旧 MEMORY.md
- **信号即 Harness**：用户每步操作产生结构化信号（SQLite 一行），AI 通过 `read_signals` 工具直读，无需中间翻译层
- **即时层零成本**：完成率、连续活跃天数等统计纯规则计算，0 token，永远新鲜
- **AI 按时间尺度分层调用**：即时规则（0 token）→ App 打开 Flash（~300 token）→ 对话中复用 Agent Loop → 周度 Pro（~2000 token）
- **Sumi 是细分场景助手**：用户模型仅服务自学场景，用 prompt 管理而非复杂推理架构

### 与 06 轮的关系

06 轮建立了评估→规划流程。07 轮让这套流程随用户演化——第三次创建项目时，Sumi 比第一次更懂用户的水平、节奏、偏好。

## 2. 智能分层与资源分配

### 按时间尺度组织 AI 调用

| Layer | 触发 | 模型 | Token/次 | 频率 | 周成本估算 |
|-------|------|------|---------|------|-----------|
| 实时统计 | 每次读取 | 规则 | 0 | 持续 | 0 |
| App 打开建议 | 每次回前台 | Flash | ~400 | ~5-10/天 | ~14,000 |
| 对话中读信号/写记忆 | 对话中 | — | 已有 | 按需 | 0（复用 Agent Loop） |
| 周度反思 | 周日/周一 | Pro+thinking | ~4,000 | 1/周 | ~4,000 |
| **合计** | | | | | **~18,000/周** |

对比旧方案（建议每 30 秒轮询 Flash）：一周 ~1,120 次 × ~300 token ≈ **336,000 token/周**。新方案用旧方案 ~5% 的资源。

### 不做什么

| 不做 | 原因 |
|------|------|
| 后台定时 AI 分析信号 | 信号本身 AI 可直读，不需要翻译层 |
| 向量搜索/embedding | 依赖外部 API，Sumi 本地优先 |
| 情绪/人格建模 | Sumi 是学习助手不是陪伴 AI |
| 定时反思 | 过于机械，移动端耗资源 |
| 建议轮询 | 高频低价值，改为 app 回前台触发 |

## 3. 三层记忆架构

### USER_MODEL.md 结构

单一 Markdown 文件，用户可直接编辑。分五个区段：

```
# Sumi 对你的理解

## 实时状态                          ← SYSTEM-MANAGED，代码自动替换
- 本周完成率：83%（15/18）
- 连续活跃：12 天
- 主要活跃时段：9:00-11:00
- 当前活跃项目：2 个
- 计划偏差率：15%（3 次拖拽换日）

## 核心记忆                          ← HOT：AI write_memory 写入，≤8 条
- [确信] 用户：Rust 所有权已掌握，trait 遇到瓶颈
- [推断] 用户偏好早上学习，晚上效率低

## 领域画像                          ← WARM：评估/规划时按项目领域注入
### Rust
- 自评水平：入门
- 学习速度：略慢于计划

## 长期偏好                          ← WARM：对话/规划时注入
- 沟通：简洁直接
- 任务粒度：偏好 20-30 分钟的碎片任务

## 归档                              ← COLD：>30 天旧记忆，不注入 prompt
```

### 各层注入策略

| 层 | 内容 | 注入时机 | Token 预算 |
|----|------|---------|-----------|
| HOT | 实时状态（系统拼接）+ 核心记忆 ≤8 条 | 每次对话 system prompt | ~350 |
| WARM | 长期偏好 | 每次对话 system prompt | ~100 |
| COLD | 归档记忆 | AI 显式调用 read_memory 才查询 | 0 |

总注入 ~450 token/次，与记忆总量脱钩。

### 各层更新机制

| 层 | 更新方式 | 频率 |
|----|---------|------|
| 实时状态 | Dart 代码拼接替换 SYSTEM-MANAGED 区块 | 每次读取前 |
| 核心记忆 | AI write_memory 工具（含自动合并） | 对话中按触发条件写入 |
| 领域画像 | 周度反思时 AI 更新 | 每周 |
| 长期偏好 | AI write_memory 或周度反思更新 | 按需 |
| 归档 | 周度反思时 AI 将 >30 天条目移入 | 每周 |

### 与旧 MEMORY.md 的区别

| | 旧 MEMORY.md | 新 USER_MODEL.md |
|------|-------------|-----------------|
| 结构 | 平面时间线 | 五区段：状态/核心记忆/领域/偏好/归档 |
| 更新 | 仅 AI 手写 | AI 手写 + 系统拼接实时状态 |
| 注入 | 全文塞入 prompt | 按层按需注入 |
| Token 控制 | 无（越记越多越膨胀） | 有（HOT ≤8 条，COLD 不注入） |
| 合并 | 纯追加 | Dice coefficient 去重/替换/矛盾标注 |

## 4. 信号体系

### 信号类型（10 种）

| 信号 | 触发操作 | 建模含义 |
|------|---------|---------|
| `todoCreated` | 用户创建待办 | 任务粒度偏好、活跃时段 |
| `todoCompleted` | 标记完成 | 执行力、完成率 |
| `todoUncompleted` | 取消完成 | 计划波动 |
| `todoDeleted` | 删除（含大改导致） | 意图变更频率 |
| `todoEdited` | 小改文本（<50% 变化） | 任务精细化习惯 |
| `todoMovedDate` | 拖拽换日 | 计划偏差模式 |
| `projectGoalSet` | 设定/修改 goal | 领域方向、自评能力 |
| `projectLevelSet` | 设定/修改 level | 能力自评准确性 |
| `projectCycleSet` | 设定/修改周期 | 时间现实感 |
| `projectTimeSet` | 设定/修改投入时间 | 可用时间模式 |

### 编辑区分

用户编辑 todo 标题时，系统用 Levenshtein 距离自动判断编辑类型：

```
用户编辑 Todo 文本
  ├─ 清空文本 → todoDeleted
  ├─ 匹配 condensedFrom（凝练还原）→ 无信号
  ├─ 小改（diff < 50%）→ todoEdited
  └─ 大改（diff ≥ 50%）→ todoDeleted + todoCreated
```

### 凝练还原保护

AI 凝练用户输入时，`TodoItem.condensedFrom` 保存原始文本。用户把凝练结果改回原始文本 → 不产生信号。这避免了"AI 凝练 → 用户还原 → 系统误判为编辑"的噪声。

### 过去日期门禁

所有信号发射前检查日期：过去日期的 todo 不产生任何信号，UI 层同时拦截所有操作，双重保障历史信号准确性。

### 信号数据格式

每条信号是结构化 JSON，AI 可直接读取：

```json
{
  "signal": "todoCompleted",
  "time": "2026-07-15T09:23:00",
  "context": {
    "title": "学 Rust 所有权",
    "plannedDate": "2026-07-15",
    "completedOnTime": true,
    "hourOfDay": 9
  }
}
```

### 存储

SQLite `signals` 表，按类型/时间/项目建立索引。append-only，不删除。

## 5. 记忆合并

### 设计

AI 调用 `write_memory` 时，系统在 tool_executor 层做本地合并判断（Dice coefficient，2-gram 重叠率），不消耗额外 AI 调用：

```
新条目 vs 已有核心记忆条目
  ├─ 相似度 > 90% → 跳过，反馈"已存在"
  ├─ 50-90% → 替换旧条目，标记"(已更新)"
  ├─ 与[确信]条目矛盾 → 追加"[待确认]"
  └─ 全新 → 正常追加
```

### 置信度标记

| 标记 | 条件 | AI 行为 |
|------|------|---------|
| `[确信]` | 用户明确表达 ≥2 次，或明确表达 + 行为一致 | 作为决策依据 |
| `[推断]` | AI 从行为模式推断，或用户只提过 1 次 | 谨慎使用 |

### write_memory 触发条件

System prompt 中列出 5 条具体触发条件（替代旧 prompt 模糊的"遇到长期偏好时写入"）：

1. 用户说了新的偏好或习惯
2. read_signals 发现了记忆里没记录的模式
3. 用户对某领域表达了瓶颈或突破
4. 用户接受/拒绝了你的建议并说明了原因
5. 新发现与已有记忆矛盾

明确不要记：信号里已有的原始事实、一次性请求、寒暄。

## 6. 动态 System Prompt

每次对话前实时构建 system prompt，不再用静态模板：

1. `computeRealtimeStats()` 从信号表规则计算本周统计（0 token）
2. `injectRealtimeStats()` 写入 USER_MODEL.md 的 SYSTEM-MANAGED 区块
3. `buildHotPrompt()` 提取实时状态 + 核心记忆（≤8 条）
4. `buildWarmPrefsPrompt()` 提取长期偏好
5. 拼接基础 system prompt + HOT + WARM + 对比清单引导

对比清单引导是末尾一行：
> 以上是对用户的已知理解。如果你在本次对话中发现了不在其中的新信息，请 write_memory

这给了 AI 一个可执行任务（"发现清单里没有的东西"），而非抽象建议。

### AI 工具

| 工具 | 改动 |
|------|------|
| `read_memory` | 改为读 USER_MODEL.md |
| `write_memory` | 增加合并判断（去重/替换/矛盾标注）+ confidence 参数 |
| `read_signals` | **新增**：可按 type/projectId/range/limit 查询历史信号 |

## 7. 建议系统

### 触发方式

- **旧**：30 秒轮询 AI 生成
- **新**：App 从后台切回前台时触发（WidgetsBindingObserver）

### 缓存策略（消除感知延迟）

```
App 回到前台
  ├─ UI 立即渲染（0ms）
  ├─ 有缓存 → 展示缓存建议
  │   无缓存 → 规则预设兜底
  └─ 后台异步：Flash 生成新建议（~1-3 秒）
      ├─ 成功 → setState 平滑替换
      └─ 失败 → 保持当前展示，用户无感知
```

### 节流规则

- 距上次 < 2 分钟 → 不刷新
- 距上次 > 30 分钟 → 强制刷新（场景可能变了）

### 规则预设（兜底，0 token）

| 条件 | 建议 |
|------|------|
| 今日有待办 + 0 完成 | "帮我规划今天的学习顺序" |
| 完成率 ≥ 70% + 有未完成 | "帮我总结一下今天的进展" |
| 完成率 100% | "今天全部完成了，回顾一下本周？" |
| 晚上 8 点后 + 完成率 < 30% | "今天先休息，明天帮你重新安排" |

## 8. 周度反思

### 触发

每周日或周一中午前自动触发一次（距上次 ≥ 6 天）。

### 输入

- USER_MODEL.md 全文
- 本周全部信号（range: 7d）

### 产出

Pro 模型 + thinking，~4000 token，更新 USER_MODEL.md：
1. 领域画像 — 更新学习速度、薄弱维度
2. 长期偏好 — 如本周行为改变了推断
3. 核心记忆 — 写入"本周洞察"
4. 归档 — 将 >30 天的条目移入归档区

### 失败处理

静默跳过，等下周。不影响日常功能。`lastWeeklyReflection` 持久化到 snapshot 防止重复触发。

## 9. 过去日期只读

### 规则

今天及未来 → 可编辑（产生信号）；过去日期 → 只读（不产生信号，不允许变更）。

### 覆盖范围

| 层级 | 限制 |
|------|------|
| 编辑面板 | TextField disabled、隐藏操作按钮、显示警告横幅、"关闭"替代保存/删除 |
| 卡片 | 完成图标变色惰性、隐藏 pin 图标、opacity 0.7 |
| 网格 | 禁用拖拽排序、滑动删除、Dismissible、LongPressDraggable |
| 信号 | 所有 emit 方法内置过去日期检查，拦截所有信号发射 |

## 10. 开发者可观测

### 信号日志页

设置 → 开发者 → 信号日志。按时间范围（7 天/30 天/全部）筛选，展示信号类型图标 + 时间 + context 摘要。

设置 → 用户模型（USER_MODEL.md）。全屏 Markdown 编辑器，带系统管理区保护警告，支持保存/清空/取消。

### 用户名片

设置页顶部展示/编辑昵称（`appSettings.userName`）。
